# 英语发音纠正助手 — 概要设计

> 本文只讲**概念与架构**,不含实现细节与代码。目的:让你形成整体认知,再据此讨论取舍。

---

## 1. 目标场景

一个英语发音教练助手,核心循环:

1. **AI 示范**:给出目标句/词,用标准发音读出来(TTS)
2. **人跟读**:用户对着麦克风模仿朗读
3. **AI 评测**:逐音素分析用户发音,找出错在哪(替换/遗漏/重音/语调…)
4. **AI 纠正**:用通俗语言讲解怎么改 + 再次示范,进入下一轮

衍生模式:自由朗读评测、最小对立对训练(ship/sheep)、跟读打分、长句流利度评估等。

**词库可自定义**(明确需求):内置课程库之外,用户可导入/指定自己的词库(单词表、
句库、专项练习集)。架构上天然支持——评测流程对任意文本做 G2P 生成参考音素,
任何词表/句库都能直接用,不需要为新词训练模型。

---

## 2. 一个关键认知(决定整套技术选型)

> **通用 ASR / Whisper / 端到端语音大模型,在这里是"错的工具"。**

它们被设计成**抗口音、理解意图**——会自动把不标准发音"脑补"成正确文本。
用户说 "I sink",它转成 "I think"。**这正好抹掉了我们要检测的错误。**

因此本系统的核心**不是"语音识别",而是"发音评测(GOP / 误读检测)"**——
一类专门的语音学技术,与对话/识别是不同范畴。LLM 在这里**只负责把评测结果讲成人话**,不参与评测本身。

---

## 3. 系统架构(组件与数据流)

```
                 ┌─────────── 目标文本 ───────────┐
                 │                                │
            (G2P 文本→音素)                  (TTS 示范)
                 │                                │
         期望音素序列 ──────┐               标准发音音频 → 播放给用户
                            │                            │
用户跟读录音 ── VAD 截取 ──→ 音素识别 / 强制对齐 ── GOP 逐音素打分
                            │                            │
                            └──→ 韵律分析(重音/语调/节奏/流利度)
                                          │
                              结构化评测报告(JSON:每音素得分、错误类型、韵律指标)
                                          │
                                   LLM(复用现有端点)
                                          │
                          人话讲解 + 改进建议 + 下一轮示范
```

### 组件职责

| 组件 | 职责 | 性质 |
|---|---|---|
| **G2P** | 目标文本 → 标准音素序列(参考答案) | 规则/小模型,轻 |
| **TTS** | 生成标准发音供跟读 | 母语音色,流式 |
| **音素识别 / 强制对齐** | 听出用户**实际发了什么音**,与参考对齐 | **核心**,语音学专用模型 |
| **GOP 打分** | 逐音素"发得有多准",定位替换/遗漏/插入 | **核心** |
| **韵律分析** | 重音、语调、节奏、流利度(与音素准确度是**两套独立分析**) | 信号处理 |
| **LLM** | 把结构化报告转成教学反馈 | **复用现有 vLLM 端点,不专门部署** |
| **VAD/ASR(可选)** | 截取语音段、给用户看"系统听到的大致内容" | 复用现有项目能力 |

---

## 4. LLM 的定位(澄清常见误解)

- LLM **不做评测**,只做"翻译":把 `/θ/ 被发成 /s/、think 重音偏移` → 变成
  "你的 think 里 th 发成了 s,舌尖轻触上下齿之间送气试试"。
- 因此**模型多大、是否多模态、是否全双工,在这个场景几乎不影响评测准确度**。
- 直接**复用现有 GB10 上的 vLLM 端点**(语音 app 已在用的同一个),零额外大模型部署成本。

---

## 5. 与现有项目的关系(复用 vs 新增)

| 现有能力 | 复用方式 |
|---|---|
| mic → cpal → 16k → VAD 管线 | 直接复用(截取跟读音频) |
| LLM 客户端(OpenAI 兼容,8085 端点) | 直接复用(反馈讲解) |
| Tauri 前后端骨架、设置体系 | 直接复用(新增"发音训练"模式 UI) |
| Whisper/SenseVoice 识别层 | **不用于评测**;可保留只做"显示听到内容" |
| 音色门控(刚做) | 可复用:确保只评测目标学习者的声音 |

**新增的核心**:发音评测引擎(G2P + 音素识别/对齐 + GOP + 韵律)+ 训练循环 UX。

---

## 6. 部署拓扑(初步设想,待讨论)

- **桌面端(Windows app)**:录音、播放、UI、训练循环编排
- **GB10(192.168.0.68)**:重的推理服务(TTS、音素评测模型、LLM 反馈)以服务形式暴露
- 评测模型很小(~3–6GB),GB10 内存/算力**绰绰有余**,瓶颈不在这
- 也可全本地(桌面端跑评测)——离线但精度/可维护性需权衡,待定

---

## 7. 待讨论的关键决策点

1. **评测引擎路线**:wav2vec2 音素直解码(轻、易部署、精度一般) vs Kaldi/MFA GOP(重、部署复杂、更稳)vs 对比商用基准(Azure Pronunciation,精度高但要云)
2. **离线 vs 服务化**:全桌面本地,还是评测放 GB10
3. **评测维度优先级**:先做"音素准确度"够不够,还是首版就要重音+语调+流利度
4. **反馈粒度**:音素级 / 单词级 / 句子级,先做哪层
5. **词库管理(已确定要支持自定义,讨论细节)**:
   - 导入格式:纯单词表 / CSV(单词+例句+标签)/ 是否带参考音频
   - 生僻词/专有名词 G2P 易错 → 是否允许手动指定 IPA、或用发音词典覆盖、或 LLM 辅助补全
   - 是否导入时预生成参考音素并缓存(性能)
   - 内置课程库 + 用户词库 + LLM 动态生成练习,三者如何并存与组织(标签/难度/弱项)
6. **可靠性容忍度**:误报"你读错了"对学习者打击大,首版如何设阈值/兜底

---

## 8. 主要风险

- **评测可靠性是真难点**:开源音素识别有错误率,易误报;GOP 更稳但部署重。需校准与"不确定就不纠"的保守策略。
- **韵律评估更难**:重音/语调主观且数据少,首版可降级或仅提示。
- **体验闭环**:示范→跟读→纠正→重试要顺,延迟和反馈措辞影响学习意愿。
- **范围蔓延**:容易想做成"全能口语外教",建议首版聚焦**单词/短句的音素级纠正**。

---

## 9. 建议的阶段划分(粗)

- **P0 最小闭环**:固定词/短句库 → TTS 示范 → 跟读 → 音素级 GOP 打分 → LLM 文字讲解 → 重试
- **P1 增强**:单词级高亮、最小对立对训练、**自定义词库导入/管理**、音色门控接入
- **P2 进阶**:重音/语调/流利度、长句段落评测、学习进度追踪
- **P3 体验**:动态生成练习、个性化弱项训练、低延迟流式反馈

---

## 10. 一句话总结

这不是"换个更大的对话模型"的问题,而是**新增一类专用的发音评测能力**:
核心在小而专的语音学模型(G2P + 音素 GOP + 韵律),LLM 仅做反馈表达且复用现有端点,
现有项目的录音/LLM/UI 骨架大部分可复用。先聚焦"单词/短句音素级纠正"的最小闭环。

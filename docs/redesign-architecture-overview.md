# 项目重构 — 总体架构概要设计

> 只讲**概念与架构取舍**,不含代码与实现细节。目的:形成整体认知,逐点讨论后再定。
> 配套阅读:`docs/pronunciation-coach-overview.md`(发音教练方向)。

---

## 1. 背景与首要目标

现状:单体 Tauri 桌面 app,本地采麦 + 本地 sherpa-onnx 识别 + 远程 vLLM 润色/翻译。
踩到的痛点:原生打包(2.6GB 模型+DLL 搬运)、ONNX 导出折腾且掉精度、模型/引擎与产品逻辑耦合。

**首要目标:最终效果最优。** 用户愿意推倒重来。
衍生约束:① 桌面端要保留"优化文本自动复制到剪贴板";② 未来要支持 ESP32 类设备只采音推流;③ 面向发音教练等新方向;④ **语言:当前中文为主、偶夹英文;未来可能出现纯英语交流场景**——ASR/LLM 选型需中文优先但保留英语/多语种路径,不写死。

---

## 2. 核心原则(一句话)

> **瘦客户端 ── 干净的音频流协议 ── GB10 作"模块化 AI 服务宿主"。**

- 推理整体上移到 GB10;客户端不再做重推理
- 引擎不再是地基,而是**每个服务内部可替换的实现**;"效果最优"靠**逐任务选 SOTA**,不被单一运行时(如 sherpa-onnx/ONNX)锁死
- 现有 vLLM 作为服务端内部依赖继续用

---

## 3. 总体拓扑

```
桌面客户端 (采音 + UI + 剪贴板/自动复制)  ┐
ESP32 / 瘦设备 (只采音, 推流, 无 UI)      ├─ 音频流协议(WebSocket) ─┐
浏览器(管理控制台: 统计/模型切换/配置)   ┘                          │
                                                                     ▼
                                  GB10  (Ubuntu aarch64 + Docker, ~128GB 统一内存)
                                  ┌─────────────────────────────────────────────┐
                                  │ 编排层(会话/业务流程/路由)                  │
                                  │   ├─ ASR 服务            (语音→文本)         │
                                  │   ├─ 发音评测服务        (GOP/音素, 可选)    │
                                  │   ├─ TTS 服务            (文本→语音)         │
                                  │   ├─ LLM = 现有 vLLM     (润色/翻译/反馈)    │
                                  │   └─ VAD / 声纹 / 词修正 等能力              │
                                  └─────────────────────────────────────────────┘
```

---

## 4. 客户端职责(按设备类型)

| 客户端 | 职责 | 为什么这样切 |
|---|---|---|
| **桌面(原生,保留)** | 采麦、UI、结果展示、**剪贴板自动复制**、设置、热键 | 剪贴板自动复制是本地 OS 操作,浏览器做不了→必须有原生客户端承接 |
| **ESP32 / 瘦设备(未来)** | 仅采麦 + 编码 + 推流;接收文本结果(可选回显/灯效) | 跑不了推理;只做"麦克风 + 网络"那一半 |
| **浏览器(管理控制台)** | **侧重管理而非采音**:录音时长统计、大模型切换、各项配置管理、查看历史 | 管理类操作不依赖本地剪贴板/麦克风,天然适合浏览器;采音仍由桌面/ESP32 负责 |

> 关键:**剪贴板属于"有桌面"的场景;ESP32 场景本就无此诉求**。服务端只有一个,客户端各取所需。

---

## 5. 音频流协议(概念,非线格式)

定位:客户端与 GB10 之间**唯一的契约**。设计要点(待讨论细节,不在本文定死):

- **传输**:WebSocket(双向、文本+二进制、ESP32 也好实现);二进制帧载 16k 单声道 PCM 或 Opus
- **会话模型**:建连→声明会话参数(模式/语言/是否要评测/是否要翻译)→持续推音频帧→服务端按需回事件(部分结果/最终段/评测/错误)
- **VAD 放哪(关键取舍)**:
  - 服务端 VAD:客户端最薄(ESP32 友好),网络多传些静音
  - 客户端 VAD:省带宽、端点更快,但 ESP32 端复杂度上升
  - 倾向:**服务端 VAD 为主**,客户端可选轻量门限(统一,利于 ESP32)
- **关注点**:延迟、背压、断线重连、鉴权(局域网可简化)、多客户端会话隔离
- **产品事件**:最终文本、优化文本、翻译、发音评测报告——均通过该协议回客户端,客户端只负责"呈现 + 本地动作(如复制)"

---

## 6. GB10 服务划分与选型候选(效果优先)

每个服务独立容器、独立选型、可单独升级。**选型在讨论后定,这里只列候选与取舍**:

| 服务 | 职责 | SOTA 候选 | 取舍要点 |
|---|---|---|---|
| **ASR** | 语音→文本 | FunASR(中文最强,SenseVoice/Paraformer 原生)/ faster-whisper · WhisperX(多语种) | **当前以中文为主、偶夹英文 → FunASR 系优先**;⚠️ **未来可能有纯英语交流场景**,需保留多语种/英语路径(faster-whisper 或语音LLM),设计上 ASR 选型做成**可按会话语言路由**,不要写死单一中文模型 |
| **发音评测** | 音素 GOP / 误读检测 | Kaldi·MFA GOP / wav2vec2 音素 + G2P | 专用领域,**不在 sherpa-onnx 范畴**;可靠性是难点 |
| **TTS** | 文本→语音(示范/回应) | Kokoro-82M / CosyVoice2 / Piper | 流式低延迟;中文音色看 CosyVoice2 |
| **LLM** | 润色/翻译/发音反馈讲解 | **现有 vLLM**(gemma-4-26B-A4B,MoE,已在) | 复用;注意端口(现 1234,app 配 8085,需统一) |
| **编排层** | 会话、流程串接、路由、业务规则 | 自研薄层 | 把上面拼成业务;声纹门控、词修正、词库在此 |

> 引擎结论:**不再锚定 sherpa-onnx**;它退为"某服务的可选实现之一"。原生 PyTorch/HF 框架优先(GB10 是原生 CUDA 强机 + Docker,SOTA 模型先出 PyTorch,ONNX 导出滞后且有损——已亲历)。

| 现有功能 | 重构后落在哪 |
|---|---|
| 采麦 / VAD 管线 | 采麦→客户端;VAD→服务端(为主) |

## 8. 部署与资源(GB10 实测依据)

- Docker 28.5 已装;CUDA 13.1;~128GB 统一内存
- 现有 vLLM `--gpu-memory-utilization 0.55` → **约一半内存(~50GB+)空闲**,足够再放 ASR/评测/TTS(这些都小,几 GB)
- 磁盘空闲 799G;局域网延迟可忽略(协议设计不必为广域网过度优化)
- ⚠️ **端口/入口要统一**:vLLM 现 1234、旧 app 配 8085——重构时定一个稳定入口(或加网关)

**部署模型(已定)**:Docker。已实测 GB10 有 `nvidia` 运行时 + NVIDIA Container Toolkit 1.18.1 → 容器内 GPU 直通可用。

- 每个服务一个容器(Python+依赖封在镜像内,主机零环境配置);`docker compose` 编排
- 多容器经 nvidia runtime 共用 GPU/统一内存
- vLLM 暂保持主机运行(非容器),不阻塞;后续可选容器化
- ⚠️ **arm64 + Blackwell 限制**:镜像必须 linux/arm64 且够新支持 CUDA 13 / sm_121;部分公共镜像仅 x86 或过旧 → 这类需基于 NVIDIA arm64 CUDA 基础镜像**自行构建**(主要工作量/风险点)

## 10. 风险

- **范围蔓延**:转写 + 发音教练 + 对话 + 嵌入式,容易摊太大。建议**先打通"转写"最小闭环**,其余按阶段加。
- **协议是长期契约**:定不好后期改动代价大,值得前期多花时间。
- **发音评测可靠性**:开源 GOP 易误报,是真难点(详见发音教练文档)。
- **端到端延迟**:多服务串接 + 网络,需流式与延迟预算贯穿设计。
- **单点依赖 GB10**:它挂了全链路停;是否要降级/容灾要早决定。
- **迁移成本**:推倒重来周期长;需明确哪些从现项目搬(VAD 经验、LLM 接入、UI、GPU 踩坑成果)、哪些重写。

---

## 11. 建议阶段划分(粗)

- **P0 最小闭环**:桌面客户端(采麦+UI+剪贴板)── 协议 ── GB10 ASR 服务 + 编排(调 vLLM 润色/翻译)。**达到并不逊于现状的转写体验**,但已是新架构。
- **P1 能力补齐**:声纹门控、词修正迁入编排;状态/历史归属落地;TTS 服务接入。
- **P2 发音教练**:发音评测服务 + 教练流程 + 词库管理(可自定义词库)。
- **P3 嵌入式**:ESP32 最小固件作为新客户端接入同协议,服务端零改。
- **P4 进阶**:实时对话/打断、个性化、低延迟流式打磨。

---

## 12. 一句话总结

不是"换个更强的引擎/模型"就完事,而是**架构层面把"采集"和"计算"彻底分离**:
瘦客户端负责采音与本地动作(桌面端含剪贴板),GB10 作模块化 AI 服务宿主,
中间用一套稳定的音频流协议连接。引擎/模型按任务选 SOTA、可替换,
现有 vLLM 复用。先打通转写最小闭环,再按阶段长出发音教练与嵌入式。

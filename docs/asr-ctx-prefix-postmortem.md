# 前缀上下文解码：上线即回滚的复盘与修复方案

**状态**：2026-09-04 上线，同日关停（`ASR_CTX_PREFIX_MAX_MS=0`，compose 与代码默认值均已改为关）。
实现仍在库里（`server/asr/ctx_prefix.py` + `app.py::_recognize_with_prev_context`），未删除。

**关停理由（precautionary，不是"已证明有害"）**：上线 12 小时里它改写了 8 次输出，
而我**没有能力判断这 8 次是改好还是改坏**——没有音频、没有参考转写，日志也没记下判断所需的
字段。一个会改写用户文本、却无法评估的东西不该在线上跑。这条理由不依赖任何后来丢失的数据。

---

## 一、这个特性想解决什么

孤立短句里中英混说的英文词常被解成汉字音节。toolkit 段 #13340：说的是
「review 一下这个文档」，得到「伪略一下这个文档。」；**同一段音频字节不动**，
前面拼一整句无关中文重解即得到「你看一下识别记录，review一下这个文档。」。

实现：短句（`< ASR_CTX_PREFIX_MAX_MS`）解码时，把上一句已完成句子的音频拼在前面重解一次，
再用上一句的识别文本做文本对齐，把前缀那部分切掉。两道闸兜底：`strip_known_prefix` 对齐不上
返回 `None`；`accept_ctx_text` 不通过则拒绝。两者都退回无上下文的结果。

### 2.1 关于那 24 次拒绝，只能说这么多

**抓取到的 12 条**里 `stripped` 全部为空（`plain='Okay.'`/`'嗯。'`/`'继续。'`/`'The.'` 这类）。
`accept_ctx_text` 第一句就是 `if not stripped: return False`（`ctx_prefix.py:83`），
在任何比例计算之前返回。所以：

- **这 12 条是在空值检查处返回的，没有走到长度比判断**；
- **另外 12 条没有抓取，形态未知**——不能断言 24 条全是空串，也不能断言长度比闸从未生效。

**「这些拒绝没有误杀」这个说法不成立**：`stripped` 为空只能说明切完没剩下东西，同样可能是
**切过头把正文一起吃掉了**。判断误杀需要音频或参考转写，日志里两者都没有
（`app.py:761` 的拒绝日志只记 `stripped` 与 `plain`）。

### 2.2 8 次改写全文

```
'啊住你你有冇啊啊。'        -> '我今天不会。'
'生产的那个app他会去处理。'  -> '生产的那个app他们去处理。'
'现在想要打饿。'            -> '现在想要把二。'
```

**这 8 条一条都没有被证实是改好或改坏。** 初稿写过「1 好 3 坏 4 无意义」，那是目测，收回。

## 三、根因

### 3.1 观测不足以定位（首要）

四条 `[asr][ctx]` 日志里只有 `prefix not located` 记了 `full` 和 `prev`（`app.py:757`）。
**改写与拒绝这两条——唯二会影响输出的分支——反而记得最少**（`app.py:761`/`764` 只有 `plain`
和结果）。而且日志只进 stdout，容器重建即丢。

后果就是 §2：事故发生后既无法判断好坏，也无法归因。**其余所有根因分析都被这一条卡住。**

### 3.2 短文本捷径（代码可证实，但后果未证实）

`accept_ctx_text` 里：`max(len(stripped), len(plain)) < SHORT_TEXT_CHARS`（8）时直接接受
（`ctx_prefix.py:88-89`），本意是「极短文本上比例判据没有意义」。

`plain='。'`（1 字）+ `stripped='恶的打强起。'`（6 字）确实是**经由这条捷径放行的**——这一点由代码
确定。但如 §2.2，**放行的是不是坏结果并未证实**。所以这条捷径的问题准确说是
「**它让长度闸在最需要把关的区间失效**」，而不是「它放行了一次编造」。

单测把这条捷径钉成了「正确行为」（`test_ctx_prefix.py` 的
`test_short_texts_are_not_judged_by_ratio_alone`）——测试写的是我设想的规则，
不是我想要的性质。

### 3.3 前缀泄漏：只是假设，无法证实

「样，」「部去」两条以疑似上一句尾部的字串开头。现有日志不记 `full`/`prev_text`，
所以分不清：

- (a) **前缀残留**——`cut` 落在前缀内部，尾巴跟着输出；
- (b) **模型幻觉**——重解对本句本身就产出了这样的开头。

两者修法相反（改切分 vs 改闸门）。**分清之前不要动任何一边。**

### 3.4 方法论错误：拿合成字符串的单测当上线依据

11 条单测全绿，但全部是手写的合成字符串——等于在考自己想得到的情况。真实 ASR 输出的形态
（垃圾短句、口水词、中英混杂、标点漂移）与设想差得远。

toolkit 早有现成的正确做法：prompt 回归集（`toolkit/scripts/asr-prompt-bench.py`）拿录下来的
真实错例重放、多次重复取通过率。这次没照做，**把生产当成了评测集**。

## 四、修复方案

顺序是硬的：没有 P0-a 就做不了 P0-b，没有 P0-b 就不该碰闸门。

### P0-a · 影子模式 + 观测（不改变任何对外输出）

> **实现状态（2026-09-04）：已落地，未部署。** `server/asr/ctx_observe.py`（队列 +
> 后台写线程 + 原子写 + 完整性校验，13 条单测）、`app.py` 的 `ASR_CTX_PREFIX_SHADOW` /
> `ASR_CTX_OBS_DIR` / `Session.obs_session_id` / `_observe_ctx`、compose 的观测卷、
> 宿主侧 TTL 清理 `scripts/asr-ctx-ttl.sh`。
> **开启影子采集** = compose 里把 `ASR_CTX_PREFIX_MAX_MS` 改回 `3000` 且
> `ASR_CTX_PREFIX_SHADOW=1`，重建镜像后重启。


> 下面写的是**必须满足的性质**。实现时若有更简单的等价做法可以替换，但这些性质
> 逐条都是被具体故障或具体代码约束逼出来的，不能省。

**为什么必须是影子模式**：功能现在是关的（`ASR_CTX_PREFIX_MAX_MS=0`），
所有调用在第一个判断就返回，**永远产不出评测所需的样本**；而评测通过前又不该让它改写用户文本。
两者构成死锁。解法是加一个独立开关 `ASR_CTX_PREFIX_SHADOW=1`：照常执行重解、切分、两道闸，
把全过程落盘，**但函数始终返回 `plain`**。

- 与 `ASR_CTX_PREFIX_MAX_MS` 正交：后者仍决定"哪些句子进入这条路径"（影子期设回 3000），
  **返回值由 SHADOW 决定**。
- **代价要认**：影子期每个短句多一次 GPU 解码，而 `finalize` 是阻塞路径，会增加这些句子的
  出字延迟。所以影子期是**有限期**（够 60 条即止，预计数天），不是长期形态。

> ⚠️ **影子模式有一条无法消除的局限：它复现不了跨句级联。**
> 正式启用时，本句被改写后的文本会被存成下一句的 `prev_text`（`app.py:809-810` 存的是
> `text`，而 `text` 在 `app.py:789` 已被 ctx 改过）；影子模式强制返回 `plain`，
> 存下去的就是未改写的文本。于是下一句的 `strip_known_prefix` 拿到的 `prev_text` 不同，
> 可能得到不同的切分与 stage。
>
> **后果**：影子语料只能评估「每一句都以前一句的原始 `plain` 为上下文」这种**单步行为**，
> 覆盖不到「前一句被改写 → 影响后一句切分」的级联路径，也覆盖不到连续改写时的误差传播。
> 这不是补字段能解决的，是影子模式的定义所致。
>
> **本方案接受这条局限，代价转移到试运行期**：级联只能在真正启用后观察，所以试运行期的
> 逐条听审与止损不是形式——**它是唯一能看到级联的阶段**。这也意味着 P0-b 通过并不代表
> 级联安全，重开后头几天要格外密集地看。

#### 性质 1：记录在声纹判定之后一次写完，不做回填

ctx 逻辑跑在声纹闸**之前**（`app.py:789` 早于 `score_speakers`/`spk_decide`/`emit_segment`），
所以"这条记录对应的段最终有没有发出去"要晚一步才知道。

**不要用"先写记录、后回填"**——JSONL 是追加式的，异步写线程可能已经落盘，原地更新做不到；
"补一条关联行"又要额外定义关联 ID、合并规则和进程中途退出的半状态。

**做法**：把 ctx 的中间结果（`stage`/`full`/`stripped`/音频等）暂存在 `finalize` 的局部变量里，
**等声纹判定出结果之后，连同发送相关字段一起作为一条完整记录入队**。
两者本来就在同一次 `finalize` 调用内，不存在跨调用问题。这样每条记录一次成型、天然终态。

**发送相关要拆成三个字段。** 影子模式下「有没有发出去」是有歧义的：`emit_segment` 会丢弃
空文本（`app.py:685-691`），所以当 `plain` 为空、`stripped` 非空、两道闸都过时，
影子线上**实际不发段**，但关掉 SHADOW 后这条会变成非空并被发出——那正是风险最高的一类
（本来没输出，启用后凭空多一条）。只用一个布尔字段，要么把这类样本误排除，要么字段名说的就是假话。

| 字段 | 含义 |
|---|---|
| `spk_emit` | 声纹闸的判定结果（与 ctx 无关） |
| `shadow_emitted` | 影子模式下**实际**有没有发出去（`spk_emit` 且 `plain` 非空） |
| `would_emit_if_enabled` | **反事实**：若关掉 SHADOW 会不会发出（`spk_emit` 且最终文本非空） |

评测入选看 `would_emit_if_enabled`——它才对应「启用后用户会看到什么」。
`shadow_emitted=false` 而 `would_emit_if_enabled=true` 的样本**必须单独挑出来重点听**。

#### 性质 2：关联键由 ASR 自己生成

ASR 侧**既没有段 ID 也没有会话 ID**：段 ID 是 orchestrator 持久化时才分配的（ASR 下行只带
文本与 `t_start`/`t_end`，`app.py:685-695`）；`Session` 也不保存任何会话标识，
`handle` 直接 `Session()`，收到 `reset` 再建一个（`app.py:878-879`、`app.py:895-901`）。

所以由 **ASR 为每个 `Session()` 生成一个 uuid4 作为 `obs_session_id`**（reset 即换新）。
记录键 = `obs_session_id + t_start_ms + t_end_ms`。仅用时间键不行——reset 后时间可能重头开始，
不同连接也会撞键，导致文件覆盖或错配。

#### 性质 3：音频由 ASR 当场落盘，且存的是拼接后的完整输入

orchestrator 的段音频只保留 1 天（每小时清理，`docs/DEPLOYMENT.md:79`），靠人工每天去抓必有
漂移窗口，最关键的那条反而可能先被清掉。所以**在做出判断的当场，由 ASR 把音频写出来**。

- **存拼接后的完整输入**（`prev_seg + gap + seg`），不是分开存两段——实际喂进模型的还包含
  运行时按 `CTX_PREFIX_GAP_MS` 生成的静音，分开存会在重放时引入长度差异。
  同时把 `gap_ms`、`prev_dur_ms`、`dur_ms` 记进 JSON，便于在完整输入里定位边界。
- **另存 `seg` 单独一份**，用于对照"无上下文"那一路。
- **格式：16kHz / mono / float32 WAV**（`soundfile` 的 `subtype='FLOAT'`）。模型收到的就是
  float32 数组，**存 PCM16 会引入量化差异**，那就不再是"生产当时真正的输入"。
- 体量：本句 <3s + 上一句 <10s，float32 约 800KB/条；按上线那 12 小时 44 条的密度，
  每天百 MB 量级，配合保留上限可控。

#### 性质 4：写入不阻塞识别，且样本要么完整要么不存在

- **非阻塞**：`_recognize_with_prev_context` 是同步函数、跑在异步 `finalize` 路径上
  （`app.py:736/768/789`）。直接同步 append，遇到慢盘/挂载卡死**不会抛异常，而是阻塞事件循环**，
  拖慢甚至冻结整个 ASR 服务。必须走**队列 + 独立后台写线程**；队列满即整条丢弃并计数，
  绝不反压识别路径。
- **原子性**：一个样本 = 一条 JSON + 两个 wav。**整体作为一个队列任务**，要么全收要么全丢。
  写盘顺序固定为：**wav 先写临时文件 → flush + fsync → 原子改名到目标路径 → 最后追加 JSONL 行
  并 fsync**。JSONL 行是"该样本完整"的提交标记。中途失败则删掉临时文件与已改名的 wav。
  只用"文件存在"当判据不够——写到一半崩溃同样会留下存在但截断的文件，所以评测侧还要按
  上面的完整性判据实际读一遍。

#### 性质 5：落盘位置、容量与数据保留

- 写**宿主机挂载目录**：当前 `asr` 只挂了 `/models`（只读，`compose.yaml:34-35`），
  容器一重建就全丢（§2 就是这么丢的）。需新增可写卷，例如 `./asr-ctx-shadow:/var/log/asr-ctx`。
- **按天切分 + 保留天数上限 + 总容量上限**，超限即停止写入并告警（不是覆盖旧数据——
  旧数据才是评测语料）。
- **这是用户语音的新增持久副本，必须当敏感数据处理**：目录权限 700；
  **保留期 = 影子期 + 试运行期，结束即整目录删除**，不留长期副本。
  但"结束"这件事不能只靠人记得或靠正常退出钩子——进程崩溃、容器重建、忘记关开关都会让它
  不发生。所以**另有一个独立的 TTL 清理**：按文件 mtime 超过 `ASR_CTX_SHADOW_TTL_DAYS`
  （**默认 30**）即删，与开关状态、与是否正常结束都无关。
  **不要设成 7 天**：影子采集要数天，之后还有人工听审、改闸门、对全部记录重跑重分类，
  可能多轮迭代；而旧语料正是重跑的依据，不能被删。7 天会让最早那批 wav 在流程走完之前先消失，
  样本量缩水且旧标注无法复核。30 天是「确定的最长期限」这一性质的下限而非期望值——
  **正常路径仍是流程一结束就整目录删掉**，TTL 只是兜底。
  **这个清理必须跑在宿主机上**（cron / systemd timer，由部署脚本一并装上），
  **不能放在 asr 容器里**——影子期结束后容器很可能就不再启动了，容器内的定时任务随之不再执行，
  而 bind mount 里的语音副本还留在宿主机上。清理失败要告警而不是静默。现有 orchestrator 音频是 1 天保留，这里实质延长了留存，
  是一次有意的、有期限的例外，不能变成常态。

#### 字段契约

`stage` 标明走到哪一步；**"未产生"与"空串"必须可区分**（`null` vs `""`）：

| `stage` | 含义 | `full` / `stripped` |
|---|---|---|
| `disabled` | 功能关闭 | `null` |
| `too_long` | 本句 ≥ `CTX_PREFIX_MAX_MS` | `null` |
| `no_prev` | 无上一句 | `null` |
| `prev_too_long` | 上一句 > `CTX_PREFIX_MAX_PREV_MS` | `null` |
| `decode_error` | 重解抛异常 | `null` |
| `not_located` | `strip_known_prefix` 返回 `None` | `full` 有值，`stripped` = `null` |
| `rejected` | `accept_ctx_text` 为假 | 两者都有值（`stripped` 可能是 `""`） |
| `unchanged` | 两道闸都过，但 `stripped == plain`，输出没有任何变化 | 两者都有值 |
| `would_apply` | 两道闸都过**且 `stripped != plain`**，但 SHADOW 开着，没有真的替换 | 两者都有值 |
| `applied` | 同上**且真的替换了输出**（SHADOW 关闭时才可能出现） | 两者都有值 |

`would_apply` 与 `applied` 语义相同，只差"有没有真的改输出"。**影子期只会出现前者，
试运行期只会出现后者**——采集、评测、止损三处脚本按各自阶段取对应的那个，不要混。

**`unchanged` 必须与它们分开**：两道闸都过但文本没变的样本不会改动任何输出，既不该混进
"实际改写"的统计口径，也不该占评测分母。§2 那 8 次是按「文本确实变了」数的，口径要一致。

其余字段：`obs_session_id`、`t_start_ms`/`t_end_ms`、`prev_t_start_ms`/`prev_t_end_ms`、
`prev_text`、`plain`、`dur_ms`、`prev_dur_ms`、`gap_ms`、
`spk_emit` / `shadow_emitted` / `would_emit_if_enabled`（见下）、
`wav_ctx_path`、`wav_plain_path`、时间戳。

### P0-b · 离线评测

> **实现状态（2026-09-04）：离线部分已落地** —— `server/asr/ctx_eval.py`（15 条单测）。
> 三个子命令：
> - `reclassify <观测目录>` —— 用**当前**闸门对全部记录重新分类。`full` 已存盘，
>   而两道闸都是纯文本函数，**改闸门后重新验收是零解码成本的**；输出会标出
>   「新放行、必须补听审」的那批。
> - `worklist <观测目录>` —— 产出待听审清单（wav 路径 + 无上下文结果 + 带上下文结果）。
> - `verdict <标注.json>` —— 吃 `{key: [good|bad|neutral|skip, ...]}`，算通过线，
>   不过则非零退出。
>
> **未做**：`--redecode`（重复 3 次解码那一步需要 GPU 模型，等有语料后在 G10 上补）。


**语料只用 P0-a 落盘的 JSONL + wav。** 不要事后抓 history：orchestrator 的
`segment_set_text` 是 `UPDATE segments SET text=?2` **原地覆盖**
（toolkit `crates/orchestrator/src/db.rs:198-203`），人工经 `/segments/{id}/text` 改过之后
无从分辨，`prev_text` 会被污染成人工修正稿。

- **分母只取 `stage='would_apply'`**、`would_emit_if_enabled=true`、且样本完整（见下）的记录。
  **理由**：只有这类会真的改动用户看到的文本，也只有它们能做「无上下文结果 vs 带上下文结果」
  的二选一判定。`not_located` 根本没有候选文本（`strip_known_prefix` 返回 `None`，
  存下来的 `full` 是"上一句+本句"的整段转写，不能拿来跟 `plain` 二选一）；
  `rejected` 与 `unchanged` 也不会改输出。把它们塞进分母只会**稀释风险**。
- **`not_located` / `rejected` / `unchanged` 单独统计发生率**，用来判断切分与闸门的行为
  （例如 §3.3 的 (a)/(b) 归因），**不进"改坏 = 0"的分母**。
- **完整性判据**：JSONL 里有该样本的行，且两个 wav 都能被完整读出、帧数与 JSON 里记的
  `dur_ms`/`prev_dur_ms`+`gap_ms` 一致。只检查"文件存在"不够——截断的 wav 照样存在。
- **样本量**：≥ 60 条 `would_apply`，覆盖 ≥ 3 天、≥ 5 个会话。
  （按上线那 12 小时 8 次改写的密度，约需 4 天。）
- **重复**：每条重复 3 次（解码不稳定——同一段音频三跑曾给出「这种页面 / 这种页面 / 这个页面」）。
- **聚合口径（定死）**：解码不稳定意味着同一条样本三次重跑可能分别落进 `would_apply` /
  `rejected` / `not_located` / `unchanged`，所以要先说清非改写轮次怎么算：
  - **没落到 `would_apply` 的那一轮**记为"该轮未改写"，**既不计好也不计坏**
    （它不会改动用户看到的东西）。
  - **样本有效性**：三轮里**至少有 1 轮是 `would_apply`** 才算有效样本，否则移出分母
    （这套闸门实际上不会在它身上改写任何东西）。
  - **按样本取最坏结果**：有效样本的若干个 `would_apply` 轮次里，**只要有 1 轮被判"改坏"，
    该样本即计改坏**。线上每次改写独立发生，多数表决会把 1/3 概率的坏结果洗掉。
- **判定**：人工听 wav，对「无上下文结果 / 带上下文结果」标 **改好 / 改坏 / 无差别**。
- **通过线**：**有效样本 ≥ 60 条**（三轮重跑后仍满足有效性判据的）、**改坏样本数 = 0**、且改好样本数 ≥ 5。
  三条缺一不可——只看「0 坏、≥5 好」，会让有效样本缩水到十几条时照样通过。

> **这条线不是安全保证。** 分母这 60 条**全部**是 `would_apply`，所以它约束的总体是
> 「**这套闸门会放行的样本**」——不是「所有进入 ctx 的候选」，也不是「所有完整观测样本」，
> 三者是不同的分母，别再套错。
>
> 即便如此，「60 条零改坏」仍**不能换算成"每次改写的改坏率上界"**：样本来自有限几天、
> 少数会话，同一条重复 3 次也不是 3 个独立样本。它只用于决定"要不要试着重开"，
> 真正的保障来自下面的试运行止损。

评测脚本放 `server/asr/`，形态照抄 `toolkit/scripts/asr-prompt-bench.py`
（多次重复、调用失败单独计数并非零退出——不能让一次服务故障伪造出一份看着像结论的数据）。

### P1 · 闸门改动（等 P0 出结果，方向基本不预设）

现在唯一能定的一条，而且**只是待验证假设，不是已知规律**：

- **`plain` 只有标点或 ≤3 个有效字符时，不接受更长的结果。**
  依据仅是 §3.2——那个区间里长度闸被捷径旁路了，等于没有把关。
  **不主张"编造总是变长"**：等长、缩短的幻觉完全可能存在，本文没有任何证据能建立那种规律。
  这条只堵"最短输入 + 大幅扩写"这一种已观察到的形态，覆盖不到别的。
  实施时删掉 §3.2 那条捷径，连同把它钉住的那条测试一起改。

**明确否掉的两个方向**：

1. 「切完的残余若以 `prev_text` 尾部字串开头即判泄漏」——与现有测试直接冲突：
   `test_does_not_overcut_when_current_repeats_prefix_words` 要求 `prev='你看一下识别记录。'`、
   `full='你看一下识别记录，识别记录里面有问题。'` 时保留 `'识别记录里面有问题。'`，
   而该残余正是以 `prev_text` 尾部字串开头。短后缀误杀合法重复，长后缀盖不住「样」「部去」。
2. 「只在原文含疑似英文/术语时触发」——**自相矛盾**：目标样本 #13340 的无上下文原文是
   「伪略一下这个文档。」，纯中文不含英文，按英文检测实现恰好不会在它最想修的那条上触发。

`MIN_PREFIX_COVERAGE`、`MAX_BLOCK_GAP` 等参数**等 P0-a 的日志分清 §3.3 的 (a)/(b) 之后再定**。

## 五、#13406：一条被我判错的关联（2026-09-04 晚订正）

**原先写的是「与本特性无关，9.69s 超过阈值未触发」。这是错的。**

订正依据：#13406 的存档文本里有一段突兀的「**部去**」——
「…到具体的中能？**部去**看一下，然后采集这些。」，而关停前的改写日志里正好有一条

```
'看一下，然后你采集这些。' -> '部去看一下，然后采集这些。'
```

**离线用同一段音频重跑 4 次，从未出现过「部去」。**

### 判错的原因：把「段」的粒度搞混了

#13406 的 9.69s 是 **orchestrator 合并之后**的段，而 ctx 作用在 **ASR 侧的句子**上。
该段中间那个约 1.93s 的停顿 > `SENTENCE_GAP_MS`（1500），所以 ASR 侧本来就切成了两句；
后半句约 2.7s **小于** `CTX_PREFIX_MAX_MS`（3000），**触发了 ctx**。
拿合并后的段长去对阈值，必然得出「没触发」的错误结论。

> **这条要记住**：`ASR_CTX_PREFIX_MAX_MS` 比的是 ASR 侧句子的时长，不是客户端/控制台
> 看到的那个段的时长。判断某个段有没有被 ctx 动过，**唯一可靠的依据是观测记录**，
> 不是段长。

### 由此得到的第一个实证

§3.3 把「前缀残留」列为**无法证实**的假设。「部去」这条给了它第一个实证支持：
该字串在离线重解里从不出现，只在带前缀的那次出现，且位置正好在句首——
符合「`cut` 落在前缀内部、尾巴跟着输出」的形态。

**但仍不足以定论**：当时的日志没记 `full`/`prev_text`，所以仍无法排除「重解时模型对本句
本身就产出了这样的开头」。P0-a 的观测上线后，这类样本会带着 `full` 和 `prev_text`
一起落盘，届时才能真正分清 (a)/(b)。

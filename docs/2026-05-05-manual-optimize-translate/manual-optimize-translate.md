# manual-optimize-translate 设计总览

## 时间
- 创建日期：2026-05-05
- 最后更新：2026-05-05

## 项目现状
- 当前应用在识别出分段文本后，会自动触发“优化 -> 翻译”两阶段后处理，并通过 `optimize_status` / `translate_status` 向前端暴露进度。
- 前端 `SegmentCard` 已能展示原文、优化文本、英文翻译以及处理中状态，但仅支持复制，不支持对单条记录显式重跑后处理。
- 后端自动链路位于 `src-tauri/src/commands/recording.rs`，其触发时机与录音识别结果绑定，适用于新分段自动处理，不适用于用户在历史列表中对某一条原始文本按需重试。
- 当前 Tauri API 仅提供 `list_segments`、`tail_segments` 等读接口，没有“按 revision / segment_id 手动发起后处理”的写接口。

## 整体目标
- 在前端分段卡片中新增“手动优化与翻译”按钮，允许用户针对单条原始文本显式触发一次后处理。
- 复用现有“两阶段、先优化后翻译”的能力，不新增平行协议；手动触发与自动触发在输出结构、状态语义和 UI 展示上保持一致。
- 明确手动触发的并发与覆盖规则，避免用户连续点击导致旧结果覆盖新结果，或自动链路与手动链路互相污染。
- 保持本次变更小而聚焦：只补充单条手动触发能力，不扩展批量重试、多语种翻译、自定义目标语言等额外功能。

## 范围与非目标
- 范围内：
  - 前端分段卡片按钮、忙碌态、错误反馈与结果刷新策略。
  - Tauri 命令层新增单条手动后处理命令。
  - 后端复用现有 LLM 优化/翻译逻辑，对指定记录执行状态重置、结果覆盖和增量回写。
  - 针对手动触发新增测试与验收用例。
- 非目标：
  - 不修改数据库表结构；优先复用现有 `revision`、状态列和结果表。
  - 不引入新的依赖、队列系统或任务持久化框架。
  - 不改变自动录音识别后的默认后处理行为。
  - 不新增“只优化”或“只翻译”两个独立按钮，本轮仅提供组合动作入口。

## 核心设计决策
- 决策 1：手动入口以 `revision` 作为目标记录标识
  - `revision` 已贯穿内存态、数据库和前端列表，是当前单条分段结果最稳定的处理目标键；优先使用它而不是重新定义任务 ID。
- 决策 2：手动触发覆盖同一条记录的现有优化/翻译结果
  - 用户点击按钮的语义是“以当前原始文本重新生成最新后处理结果”，因此允许覆盖该 `revision` 既有 `text_optimized` / `text_english`。
- 决策 3：状态字段复用，不新增 `manual_*` 状态
  - 手动链路仍使用 `pending/running/success/failed/blocked`，避免前后端状态机分叉；“是否手动触发”仅体现在命令入口和日志上下文中。
- 决策 4：单条互斥，禁止同一 `revision` 并发重复执行
  - 同一条记录若已处于手动处理中，再次点击直接拒绝，前端展示忙碌态，后端返回明确错误，避免重复计费和结果竞态。
- 决策 5：结果刷新优先复用现有轮询机制
  - 录音进行中继续靠内存轮询；非录音状态下，手动触发完成后通过刷新该条记录所在列表或重新拉取最近分段，避免额外引入事件推送。
- 决策 6：手动任务不参与“latest-only 跳过旧 revision”规则
  - 自动链路里的“旧 revision 标记 skipped”是为流式录音降噪设计；用户手动指定历史条目时，应按目标条目完整执行，不因存在更新 revision 而被跳过。

## 风险与待定项
- 风险 1：手动重跑会覆盖旧的优化/翻译结果，若用户希望保留历史版本，现有表结构无法直接提供版本审计。
- 风险 2：录音中的自动链路与用户手动触发可能同时命中同一条最新分段，需要明确定义互斥规则，避免状态抖动。
- 风险 3：前端若只做全量刷新，频繁手动触发时可能产生不必要的列表闪烁，需要控制局部更新策略。
- 风险 4：当前 `perform_postprocess_and_copy` 默认包含自动复制逻辑；若手动触发也自动改写剪贴板，可能与用户预期不符，需要实施时明确。
- 待定项 1：手动触发是否允许在录音进行中对“最新分段”执行，还是仅允许对已稳定分段执行。
- 待定项 2：手动触发完成后是否发送系统通知；默认建议不发送，避免和自动识别通知混淆。
- 待定项 3：失败提示粒度是否仅展示“优化失败/翻译失败”，还是补充后端错误原因摘要。

## 详细设计

### 1. 后端单元与集成测试

- 状态机测试：`not_ready -> ready -> checking -> keep/discard/check_failed`。
- 规则层测试：短词、语气词、单姓名、重复词命中。
- LLM 解析测试：合法 JSON、缺字段 JSON、非 JSON。
- 幂等测试：同一 `revision` 并发触发只执行一次。
- 落库测试：`is_discarded` 与理由字段准确写入。

### 2. 前端行为测试

- 事件驱动移除：接收 `segment_discarded` 后状态树变更正确。
- 轮询兜底移除：事件缺失时依赖接口过滤仍一致。
- 交互稳定性：移除正在选中卡片不会导致空引用报错。

### 3. 端到端手工验收

建议使用固定样本集：
- 样本 A：`ok`（应丢弃）
- 样本 B：`张三`（应丢弃）
- 样本 C：`明天下午三点和客户开会`（应保留）
- 样本 D：`嗯...`（应丢弃）
- 样本 E：`把这个问题分成三步解决`（应保留）

验收步骤：
1. 录音或注入样本，等待优化翻译完成。
2. 观察是否在终态后触发判定。
3. 验证被丢弃条目是否从前端即时移除。
4. 验证历史查询默认不返回已丢弃条目。
5. 检查日志中是否保留判定来源和置信度。

### 4. 指标与观测

上线后至少统计：
- `discard_rate`：被丢弃分段占比。
- `rule_hit_rate`：规则层命中占比。
- `llm_discard_rate`：LLM 判定丢弃占比。
- `check_failed_rate`：判定失败占比。
- `user_restore_request_count`：用户反馈误杀次数（若后续补恢复入口）。

## 测试案例

1. 低信息量样本被稳定丢弃，高信息量样本稳定保留。
2. 在无 VAD 显式结束事件时，静默 10000ms（10 秒）仍能触发判定。
3. 判定失败不会阻断主流程，记录进入 `check_failed`。
4. 丢弃事件与轮询并存时无 UI 抖动与回弹。
5. 指标日志字段完整，支持按 `revision` 追溯。

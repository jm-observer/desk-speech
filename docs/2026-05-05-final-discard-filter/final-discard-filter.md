# final-discard-filter 设计总览

## 时间
- 创建日期：2026-05-05
- 最后更新：2026-05-05

## 项目现状
- 当前链路以分段识别为核心，在每次分段后执行优化与翻译，并将结果显示到前端列表。
- 现状缺少“最终质检”步骤，导致一些低信息量结果（如单独 `ok`、孤立姓名、纯语气词）也会进入历史。
- 前端当前主要通过拉取/轮询记录展示分段，尚未定义“该分段被后置判定丢弃”的显式协议。

## 整体目标
- 在“优化与翻译完成、且分段不再追加”后，新增一次大模型终态判定，输出 `KEEP` 或 `DISCARD`。
- 若判定为 `DISCARD`，后端将该分段标记为已丢弃，并向前端发送可消费的结果，前端立即移除该条识别。
- 判定流程采用“规则兜底 + LLM 判断”组合，降低误判与模型异常导致的噪音。
- 保持变更小而聚焦：不改动现有识别与优化主流程，只在末端新增质检阶段。

## 核心设计决策
- 决策 1：判定时机后置
  - 仅在分段进入“终态候选”后执行判定，避免中间文本不完整导致误杀。
- 决策 2：终态定义采用“双触发条件”
  - 优先上游明确结束事件（如 stream end / VAD end）；若无明确事件，则采用静默超时窗口兜底。
- 决策 3：保留软删除，不做物理删除
  - 先将记录标记为 `discarded` 并保留原因，便于追溯与阈值调优。
- 决策 4：前端接收明确丢弃信号
  - 后端在落库后发送“分段已丢弃”事件，前端据此即时移除，无需等下一轮全量刷新。
- 决策 5：模型输出强约束
  - LLM 必须结构化返回：`decision`、`confidence`、`reason`，并配合规则层做容错。

## Plan 拆分

| Plan | 名称 | 描述 | 依赖 | 顺序 | 状态 |
| --- | --- | --- | --- | --- | --- |
| Plan 1 | 终态判定时机与状态机设计 | 定义“何时判定”“如何避免重复判定”以及 VAD/静默规则 | 无 | 1 | 待开始 |
| Plan 2 | 丢弃判定协议与后端编排 | 定义规则层与 LLM 层组合、返回结构、落库字段与错误边界 | Plan 1 | 2 | 待开始 |

执行顺序：Plan 1 -> Plan 2 -> Plan 3 -> Plan 4。

## 风险与待定项
- 风险 1：静默超时阈值设置过短会误触发终态，过长则增加展示延迟。
- 风险 2：LLM 偶发格式错误会影响判定稳定性，需要严格解析兜底。
- 风险 3：若前端仅依赖轮询，移除动作可能滞后，需事件与轮询并存。
- 待定项 1：`discarded` 记录是否在“历史查询”默认隐藏，建议默认隐藏并提供可选查看。
- 待定项 2：是否允许用户手动“恢复已丢弃记录”，本轮先不包含恢复能力。

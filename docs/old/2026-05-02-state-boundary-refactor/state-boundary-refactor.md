# 状态边界重构

## 时间
- 创建时间：2026-05-02
- 最后更新：2026-05-02

## 项目现状
- `AppState` 同时承载 Tauri 命令层、Tokio 后台任务、录音同步热路径的共享状态。
- 已移除全仓 `blocking_read`、`blocking_write`、`blocking_lock` 与 Tokio 锁 `await` 混用。
- 当前共享状态统一改为标准库同步锁，并通过公共辅助函数封装中毒恢复与锁获取细节。
- 命令层、录音热路径、导出逻辑、纠错引擎与数据库访问已使用同一套锁模型。

## 整体目标
- 明确同步路径与异步路径的状态边界，消除 Tokio 锁在同步/异步混用场景下的运行时 panic 风险。
- 统一命令层访问模式，避免继续扩散 `blocking_*`。
- 为后续继续拆分 DB 访问与录音热路径建立稳定边界。

## Plan 拆分
- Plan 1：命令层异步化与状态访问统一。
  - 描述：将设置、设备、初始化等直接访问 Tokio 锁的命令层改为 `async fn`，统一使用 Tokio 异步锁访问异步状态；DB 读命令在 Plan 3 统一收口。
  - 依赖：无
  - 顺序：1
  - 状态：已完成
- Plan 2：录音/导出热路径状态拆分。
  - 描述：将录音实时路径和导出路径依赖的共享状态从 Tokio 锁中剥离，改为同步锁或更适合的同步结构。
  - 依赖：Plan 1
  - 顺序：2
  - 状态：已完成
- Plan 3：DB 访问边界收口。
  - 描述：减少命令层直接持有 DB 锁的模式，明确读写策略，避免同步阻塞路径扩散。
  - 依赖：Plan 1
  - 顺序：3
  - 状态：已完成

## 风险与待定项
- `recording.rs` 仍然承担较多职责，但锁模型已统一；后续若继续重构，应把录音状态管理、LLM 后处理、DB 落盘进一步拆分为更小模块。
- `SpeechDatabase` 目前使用同步 SQLite 连接与同步锁模型，适合当前命令/热路径边界；若未来需要高并发异步查询，可再单独设计 DB actor。

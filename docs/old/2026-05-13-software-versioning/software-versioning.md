# software-versioning 设计总览

## 时间
- 创建日期：2026-05-13
- 最后更新：2026-05-14

## 项目现状
- 当前项目已经在多个构建入口分别维护应用版本号：
  - `src-tauri/Cargo.toml` 的 `[package].version = "1.13.0"`
  - `src-tauri/tauri.conf.json` 的 `"version": "1.13.0"`
  - 根目录 `package.json` 的 `"version": "1.13.0"`
- 前端与后端运行时都没有统一的“软件版本信息”接口。前端只能拿到初始化状态、设置项和业务数据，无法显式得知当前软件版本、构建渠道或兼容信息。
- 项目内已经存在两类“局部版本”：
  - 规则版本：`correction_rule_versions.version`
  - 配置 schema 版本：`QualityFilterConfig.version`
- 上述局部版本仅服务于各自模块，不等价于整个软件版本，当前命名上也容易与应用版本混淆。
- 发布链路依赖 `v*` 标签触发 Release，但缺少一份明确的版本治理设计，无法约束“谁是单一真源、谁负责同步、运行时如何暴露、升级后如何判定兼容”。

## 整体目标
- 为软件引入统一、可追踪、可对外暴露的“应用版本”概念，并与现有“规则版本”“配置 schema 版本”做清晰分层。
- 规定应用版本的单一真源、派生字段、构建注入方式和前后端读取路径，避免多个清单文件手工维护导致漂移。
- 为未来的升级提示、兼容迁移、问题排查和发布自动化提供稳定基础，而不改变现有核心识别流程。
- 保持现有技术栈，不新增依赖；优先使用 Cargo 环境变量、Tauri 配置和现有命令通道完成设计。

## 范围与非目标
- 范围内：
  - 统一“软件版本”数据模型与命名边界。
  - 设计后端命令与前端类型，使运行时可以读取版本信息。
  - 设计版本与本地数据兼容关系，包括数据库 schema、配置 schema、规则版本的职责划分。
  - 设计发布前校验与测试策略，确保版本号同步和对外展示一致。
- 非目标：
  - 本轮不引入在线升级、自动下载更新、灰度发布或远程版本检查服务。
  - 本轮不重构数据库表结构，仅在需要时补充最小元数据存储。
  - 本轮不调整现有业务逻辑含义，例如录音、分段、LLM 后处理流程。

## 核心设计决策
- 决策 1：区分“应用版本”和“模块内部版本”
  - `app_version` 表示软件发行版本，遵循 SemVer 风格字符串，例如 `1.14.0`。
  - `schema_version` 表示本地配置或协议结构版本，服务迁移逻辑，不直接面向用户展示。
  - `rule_version` 保持为规则集内部递增版本，不与应用版本共享字段或含义。
- 决策 2：以 Cargo 包版本作为应用版本单一真源
  - 运行时代码天然可通过 `env!("CARGO_PKG_VERSION")` 读取。
  - 其他文件如 `tauri.conf.json`、`package.json` 保持为派生值，统一通过发布脚本或校验流程同步。
- 决策 3：版本信息对外暴露为独立结构体
  - 不把 `version` 混入 `InitStatus` 或设置接口，避免初始化状态和软件元信息耦合。
  - 新增独立 `get_app_version_info` 命令，前端按需调用。
- 决策 4：兼容判断基于“能力边界”而非字符串比较散落在业务代码中
  - 版本字符串用于展示与排障。
  - 迁移决策由具名 schema/version 常量控制，避免用 `if app_version < x.y.z` 直接驱动底层数据迁移。
- 决策 5：发布校验前置
  - 在发版前校验 Cargo、Tauri、npm 清单中的版本一致性，避免构建产物与 UI 展示版本不一致。

## 目标数据模型

建议新增统一运行时返回模型：

```text
AppVersionInfo {
  app_version: String,
  app_name: String,
  build_profile: String,
  git_commit: Option<String>,
  schema_version: u32,
  config_schema_version: u32,
  first_run_after_upgrade: bool,
}
```

字段语义：
- `app_version`：当前软件发行版本，来源于 Cargo 包版本。
- `app_name`：对外展示名称，默认来自 Tauri 产品名或常量。
- `build_profile`：`debug` / `release`，用于排障。
- `git_commit`：可选提交哈希；本轮允许为空，后续如需可由构建脚本注入。
- `schema_version`：数据库迁移体系当前版本号。
- `config_schema_version`：配置结构当前版本号，初期可由质量过滤等配置统一汇总而来。
- `first_run_after_upgrade`：本地存储的最近运行版本低于当前版本时为 `true`，用于前端展示升级提示。

## 风险与待定项
- 风险 1：当前版本号已散落在 Cargo、Tauri、npm 三处，若没有自动校验，后续仍可能人工修改不一致。
- 风险 2：如果将“数据库迁移版本”和“应用版本”混为一谈，未来会在补丁发布时产生不必要的数据升级噪音。
- 风险 3：`first_run_after_upgrade` 需要可靠的本地持久化位置；若写入失败，升级提示可能重复出现。
- 待定项 1：`git_commit` 是否纳入本轮实现。若缺少稳定构建脚本注入机制，本轮可先保留为 `None`。
- 待定项 2：`app_name` 是否采用 `StreamSpeech` 还是沿用当前 `productName`；需在实现时统一对外文案。
- 待定项 3：项目当前未见根级 `schema/` 目录；若新增版本信息协议 schema，需要先明确目录布局并纳入仓库。（已创建 `schema/app-version-info.json`）

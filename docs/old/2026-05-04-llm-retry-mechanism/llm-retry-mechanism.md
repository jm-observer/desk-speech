# llm-retry-mechanism 设计总览

## 时间
- 创建日期：2026-05-04
- 最后更新：2026-05-04

## 项目现状
- 当前 LLM 后处理入口为 `src-tauri/src/llm_client.rs` 中的 `optimize_text()` 与 `translate_text()`。
- 两个函数当前都采用单次执行模式：`chat_json_completion()` 成功后再调用 `extract_json()`，最后用 `serde_json::from_value()` 反序列化目标结构。
- 失败域覆盖网络请求、空响应、返回内容包裹了额外文本、以及 JSON 结构不匹配等场景；任一环节出错都会直接返回 `Err(String)`。
- `src-tauri/src/commands/recording.rs` 中的 `perform_postprocess_and_copy()` 依赖上述函数结果推进状态机，因此单次瞬时异常会把优化或翻译阶段直接标记为失败。

## 整体目标
- 为 `optimize_text()` 和 `translate_text()` 引入统一的异步重试机制，提高短暂网络抖动、模型瞬时异常和格式波动下的成功率。
- 将重试粒度控制在一次完整的“请求 LLM -> 提取 JSON -> 反序列化目标字段”链路，而不是仅重试网络层。
- 保持现有对外接口稳定：`optimize_text()` 与 `translate_text()` 继续返回 `Result<String, String>`，调用方无须感知额外控制流变化。
- 保持现有技术栈，不新增依赖，不在异步流程中引入阻塞逻辑。

## 范围与非目标
- 范围内：`src-tauri/src/llm_client.rs` 的重试常量、内部通用重试辅助函数、`optimize_text()` / `translate_text()` 重构、相关测试补充。
- 范围内：必要时补充 `recording.rs` 的日志观察点说明，但不调整其状态机语义。
- 非目标：
  - 不改动 `list_models()`、模型缓存逻辑或设置页配置结构。
  - 不在本轮引入可配置退避策略、熔断器或按错误类型差异化重试。
  - 不改变数据库写入流程与前端展示逻辑。

## 核心设计决策
- 决策 1：默认固定重试上限
  - 首轮采用代码内具名常量，默认最多重试 3 次，避免把尚未验证的参数暴露到配置层。
- 决策 2：重试覆盖完整后处理链路
  - 一次尝试应同时包含请求、提取 JSON、反序列化三个步骤，确保“响应到达但格式错误”的情况也能被自动恢复。
- 决策 3：失败日志在重试边界记录
  - 单次尝试失败使用 `warn!` 记录，最终失败继续向上返回错误；由调用方决定是否记录最终 `error!`，避免多层重复打印。
- 决策 4：等待策略显式命名
  - 重试次数与间隔不写魔法数字，统一提取为常量，后续若改为配置项可平滑迁移。
- 决策 5：测试聚焦纯逻辑可验证部分
  - 不依赖真实 LLM 服务做单元测试；通过可注入闭包验证重试次数、成功返回与最终失败路径。

## Plan 拆分

| Plan | 名称 | 描述 | 依赖 | 顺序 | 状态 |
|---|---|---|---|---|---|

执行顺序：Plan 1 -> Plan 2 -> Plan 3 -> Plan 4。

## 风险与待定项
- 风险 1：固定重试会增加单次后处理最坏耗时，需确保调用方状态更新不会误导用户为“卡死”。
- 风险 2：若模型稳定返回同类错误 JSON，重试只会放大耗时与费用，不能替代提示词治理。
- 风险 3：当前错误类型使用 `String`，会限制后续按错误类别细分重试策略的能力。
- 待定项 1：`max_retries = 3` 的语义需在实现时明确为“总尝试次数 3 次”还是“失败后额外重试 3 次”，文档与代码必须保持一致。
- 待定项 2：是否需要对 `optimize_text()` 和 `translate_text()` 使用相同的重试参数；本轮默认相同，后续若成本差异明显再拆分。

# Plan 4: 添加单元测试验证重试逻辑

## 前置依赖
Plan 3

## 本次目标
补充围绕 `retry_task()` 和 JSON 解析链路的测试设计，确保该机制对正常、边界和异常路径都有明确验收标准。

## 涉及文件
- `src-tauri/src/llm_client.rs`

## 详细设计
由于项目当前不引入新的 HTTP mock 依赖，本 Plan 以单元测试和纯逻辑闭包测试为主，不要求接入真实 LLM 服务。

### 测试策略
- 第一层：`retry_task()` 的纯逻辑测试
  - 使用计数器闭包模拟失败和成功，无需真实网络请求。
  - 重点验证尝试次数、最终返回值和“最后一次错误”语义。
- 第二层：`extract_json()` 与反序列化兼容性测试
  - 继续覆盖纯 JSON、带包裹文本 JSON、完全非法内容。
  - 必要时增加字段缺失或类型不匹配案例，确保这些错误能在 Plan 3 中被视为可重试失败。
- 第三层：接入点验收
  - 若实现允许注入内部步骤，可对 `optimize_text()` / `translate_text()` 做轻量包装测试。
  - 若当前结构不便注入，则至少保证 `retry_task()` 和 `extract_json()` 的组合语义在文档中被明确定义，并通过已有单测覆盖关键分支。

### 建议测试用例
- 用例 1：首次成功
  - 闭包第一次执行即返回 `Ok("value")`，断言只调用 1 次。
- 用例 2：失败后恢复
  - 前 2 次返回 `Err`，第 3 次返回 `Ok`，断言最终成功且总调用次数为 3。
- 用例 3：达到上限后失败
  - 连续失败直到耗尽尝试次数，断言返回最后一次错误文本。
- 用例 4：零值参数保护
  - `max_attempts = 0` 时仍至少执行 1 次，避免无执行分支。
- 用例 5：JSON 提取失败
  - 输入无 JSON 内容，断言报错信息稳定可识别。
- 用例 6：字段结构不匹配
  - 返回 JSON 结构合法但缺少目标字段，断言反序列化失败被正确冒泡。

## 验收标准
- 新增测试均可在现有 test framework 下稳定运行，不依赖网络环境。
- 测试名称能直接表达场景和预期，便于后续回归排查。
- 覆盖至少一个正常路径、两个恢复路径和两个最终失败路径。

## 测试案例
- `cargo test --workspace` 通过。
- 若实现中新增异步测试，需使用现有 `tokio` 测试能力，不引入新依赖。

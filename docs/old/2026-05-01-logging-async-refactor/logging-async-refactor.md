# logging-async-refactor 设计总览

## 时间
- 创建日期：2026-05-01
- 最后更新：2026-05-01

## 项目现状
- 后端主逻辑集中在 `src-tauri/src/lib.rs`。
- 目前存在大量 `eprintln!` 日志输出，未统一通过 `log` crate 管理。
- 存在多处 `std::thread::spawn` 后台线程，生命周期和错误传播边界不统一。
- `src-tauri/src/main.rs` 入口当前为同步 `fn main()`，仅调用 `run()`。
- 已存在 `log` 依赖，但日志初始化与日志级别策略尚未形成统一规范。

## 整体目标
- 将应用日志统一改为 `log` 宏（`info!`/`warn!`/`error!`/`debug!`）。
- 将“新建后台执行单元”从同步线程模型迁移到异步任务模型（基于 `tokio` / `tauri::async_runtime`）。
- 从应用入口开始，建立一致的异步启动与任务调度路径。
- 在不改变现有业务行为的前提下完成重构，并补充必要测试。

## 已确认范围与决策
- “新建进程改异步任务”等价为：现有 `std::thread::spawn` 全部迁移为异步任务。
- 入口策略采用：保持 Tauri `main` 形态，不强制引入 `#[tokio::main]`，通过异步 runtime 调度启动链路。

## Plan 拆分

| Plan | 描述 | 依赖 | 顺序 | 状态 |
|---|---|---|---|---|
| Plan 1 | 日志体系改造：`print/eprint` 全量替换为 `log`，补齐日志初始化与级别约定 | 无 | 1 | 待开始 |
| Plan 2 | 并发模型改造：`std::thread::spawn` 迁移为异步任务，梳理停止信号与错误上报 | Plan 1 | 2 | 待开始 |
| Plan 3 | 入口异步化：从 `main` 到核心启动链路统一异步执行，补充回归测试并完成修复流程 | Plan 1, Plan 2 | 3 | 待开始 |

## 风险与待定项
- 部分初始化任务可能涉及 CPU 密集构建，需评估是否使用 `spawn_blocking`，避免阻塞异步调度。
- 线程迁移为异步任务后，需要重点验证停止时序与资源回收（音频流、通道、数据库写入任务）。

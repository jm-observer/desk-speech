# split-optimize-translate 设计总览

## 时间
- 创建日期：2026-05-01
- 最后更新：2026-05-01

## 项目现状
- 当前后处理链路将“文本优化 + 英文翻译”合并在一次请求中执行。
- 合并请求在出现英文翻译异常时，容易影响整体结果稳定性：优化文本与翻译结果耦合，失败定位和降级策略粒度不足。
- 现有前端展示与后端状态管理主要围绕单次后处理完成事件组织，缺少“分阶段完成”的明确状态语义。

## 整体目标
- 将后处理链路拆分为两个有序步骤：
1. 第一步：仅执行文本优化（源语言内优化）。
2. 第二步：以优化后的文本为输入执行英文翻译。
- 保证步骤间依赖明确：翻译必须依赖优化成功产物，不再直接基于原始文本翻译。
- 将失败域隔离：翻译失败不回滚已成功的优化结果，用户仍可获得稳定优化文本。
- 增强可观测性：分别记录优化与翻译的耗时、状态、错误上下文，便于排障与质量评估。

## 范围与非目标
- 范围内：后端任务编排、状态机与存储字段扩展、前端展示状态调整、测试补充。
- 范围内：保持现有 OpenAI 兼容接口能力，不引入新依赖。
- 非目标：
  - 不改动 ASR 识别主流程。
  - 不引入多语种翻译扩展（本轮仅英文翻译）。

## 核心设计决策
- 决策 1：串行两阶段执行
  - 对同一条文本，严格按”优化 -> 翻译”顺序执行，禁止并行触发。
- 决策 2：分阶段独立状态
  - 维护 `optimize_status` 与 `translate_status` 两套状态，避免单状态混淆。
- 决策 3：分阶段事件推送
  - 优化完成后立即推送一次结果；翻译完成后推送二次增量更新。
- 决策 4：错误降级最小化影响
  - 优化失败：停止后续翻译，并保留原始文本显示。
  - 翻译失败：保留已优化文本，翻译字段置空并上报可观测错误。
- 决策 5：双系统提示词配置
  - 原单一 `prompt_template` 拆分为 `optimize_prompt_template`（文本润色）和 `translate_prompt_template`（英文翻译），各自独立配置、独立默认值，用户可在设置界面分别编辑。
- 决策 6：数据库迁移与历史兼容
  - 通过 `0002_split_optimize_translate.sql` 迁移文件扩展表结构；`asr_raw_records` 新增双状态列，`asr_llm_results` 重建为可空字段 + 错误/时间戳列；旧数据通过 UPDATE 语句映射到新字段，旧列保留不删除。

## 风险与待定项
- 风险 1：两阶段请求增加总耗时，需通过异步编排与增量回传降低体感延迟。
- 风险 2：分阶段状态写入在高并发下可能发生竞态，需结合 latest-only 语义避免旧任务覆盖新结果。
- 风险 3：若优化结果风格偏差过大，可能放大翻译误差，需在提示词中增加约束（忠实语义、避免扩写）。
- 风险 4：数据库迁移中 `asr_llm_results` 需要重建表（SQLite 不支持 ALTER COLUMN），需在事务中执行确保原子性。
- 待定项 1：翻译失败重试策略是否启用（默认建议关闭，避免重复费用与延迟抖动）。
- 待定项 2：前端是否展示分阶段耗时明细（默认仅记录日志，不在 UI 首屏展示）。
- 待定项 3：旧 `prompt_template` 迁移策略——若用户已自定义旧提示词，是否尝试拆分复用到 `optimize_prompt_template`，还是直接使用新默认值。

# P0 落地拆解 — 客户端/服务端最小闭环

> 概念级,无代码。基于已锁定决策 A–E(见 `redesign-architecture-overview.md` §9)。
> 目的:先过一遍 P0 怎么落地、目录怎么分、协议长什么样,确认后再动代码。

---

## 1. P0 目标(范围红线)

**做到:转写体验不逊于现状,但已是"瘦客户端 + GB10 服务"新架构。**

闭环:
```
桌面客户端(采麦 → 推流) ──协议──→ GB10:
        ↑                         ├ ASR 服务(FunASR,含 VAD)
   文本/优化文本回显               └ 编排层(调 vLLM 润色/翻译)
        ↑──────────────── 结果(段/优化/翻译)经协议回客户端
   桌面端本地:剪贴板自动复制
```

**P0 不做(推迟到 P1+)**:声纹门控、发音评测、TTS、ESP32、浏览器管理台、离线降级。

---

## 2. 分支与目录结构(决策 A/B/C)

当前仓 `redesign/client-server` 分支内:

```
/                     现有 Tauri 工程(桌面客户端,复用)
  src-tauri/          Rust 后端:去掉本地 sherpa-onnx 识别,改为协议客户端
  src/                前端 UI:基本沿用(录音/结果/设置/复制)
/server/              新增,服务端,GB10 上 Docker 跑
  asr/                FunASR ASR 服务(容器1,Python sidecar:用其自带 server,
                      或仅极薄 Python 包装——属"运行/配置"非项目代码)
  orchestrator/       编排层(容器2,**Rust**):会话、调 ASR、调 vLLM、状态/历史;
                      复用现有 Rust 代码(词修正/分段/LLM 客户端/设置)
  compose.yaml        docker compose 编排
/docs/                设计文档(已在)
```

- 客户端 = Rust/Tauri(复用现有壳、UI、剪贴板、设置)
- 编排层 = **Rust**(业务胶水,不做推理,大量复用现有 Rust 代码)
- asr = Python sidecar 容器(FunASR 自带 server 优先;不够再加薄包装);vLLM 维持主机现状
- 旧的本地识别相关 Rust 代码(sherpa-onnx 调用、模型管理)在客户端**下线**

---

## 3. 音频流协议(P0 最小形态,概念)

客户端 ↔ 编排层之间唯一契约。P0 只需覆盖"音频进 / 文本出":

- **传输**:WebSocket(一条连接=一个录音会话)
- **建连**:客户端发会话参数(语言=zh/auto、是否要翻译、是否要优化)
- **上行**:持续发二进制音频帧(16k 单声道 PCM,P0 先不上 Opus,简单优先)
- **下行事件**(JSON):
  - `segment`:一段最终识别文本(含时间)
  - `optimized`:LLM 优化后文本
  - `translated`:翻译文本(若开启)
  - `error` / `status`:错误、就绪/忙
- **VAD 在服务端**(决策 E):客户端只管推流,FunASR 服务侧做 VAD 切段
- **结束**:客户端发结束帧或断连 → 服务端 flush 最后一段

> 协议刻意先做窄(只音频/文本)。发音评测/TTS/对话等以后**扩事件类型**,不推翻。

---

## 4. 桌面客户端改造(复用为主)

| 模块 | P0 怎么处理 |
|---|---|
| 采麦 cpal → 16k 重采样 | **保留**,产出 16k PCM 帧 |
| 本地 VAD + sherpa-onnx 识别 | **移除**,改为把 PCM 帧经 WebSocket 推给服务端 |
| 结果/分段 UI | 沿用,数据来源从本地改为协议下行事件 |
| 剪贴板自动复制(优化文本) | **保留在客户端本地**(收到 `optimized` 事件后本地写剪贴板) |
| 设置(语言/是否翻译等) | 沿用;模型/服务级配置 P0 先简化(后续归浏览器管理台) |
| GPU 构建/打包那套 | **不再需要**(客户端无重推理)——顺带摆脱之前 DLL/2.6GB 打包之苦 |

---

## 5. GB10 服务端(决策 B,Docker)

- **asr 容器**:FunASR(Paraformer/SenseVoice 系)+ VAD + 标点/ITN;暴露内部接口给编排层;arm64 镜像需基于 NVIDIA arm64 CUDA 基础镜像自构建(主要风险点)
- **orchestrator 容器(Rust)**:WebSocket 服务(对客户端);收音频→转给 asr→拿文本→调 vLLM 优化/翻译→把事件回推客户端;P0 内置最小会话与历史存储(服务端集中)。复用现有 Rust:LLM 客户端、分段/合并、词修正、设置/DB。静态二进制,容器极小
- **vLLM**:主机现状不动,编排层用 HTTP 调它;P0 顺带把入口/端口理顺(1234/8085)
- **compose.yaml**:一键起 asr + orchestrator;GPU 经 nvidia runtime

---

## 6. 一次说话的端到端流(P0)

1. 用户点"开始录音" → 客户端建 WebSocket 会话(带语言/翻译选项)
2. 客户端持续推 16k PCM 帧
3. orchestrator 把音频喂 asr 服务;FunASR VAD 切段、识别
4. 出一段 → orchestrator 回 `segment`;并行调 vLLM 优化(+翻译)→ 回 `optimized`/`translated`
5. 客户端显示;收到 `optimized` 按设置自动写入剪贴板
6. 停止 → flush 收尾,关会话

## 8. P0 验收标准

- 桌面端录中文短句,经 GB10 返回识别文本,**质量不逊于现状(FunASR 中文应≥SenseVoice)**
- LLM 优化/翻译正常,优化文本**自动复制到剪贴板**(行为对齐现状)
- 局域网下端到端延迟可接受(目标:与现状本地识别相当或更好)
- 关闭客户端不残留;断线能重连或干净结束

---

## 9. P0 风险/未知

1. **FunASR arm64 + Blackwell 容器**:可能要自行构建镜像、踩 CUDA13/sm_121 兼容——**P0 最大不确定项**,建议第一步就做可行性验证(先把 FunASR 在 GB10 Docker 里跑通一段音频)
2. **服务端 VAD 延迟/切段**:体验是否仍"跟手",需实测调参
3. **协议虽窄但是长期契约**:P0 就把扩展性留好(事件类型可加)
4. **vLLM 入口**:端口/网关理顺,避免又出 1234/8085 混乱
5. 网络/会话健壮性:断线、背压、并发会话(P0 单用户可简化)

---

## 10. 建议的 P0 执行顺序

1. **可行性先行**:GB10 上把 FunASR 跑进 Docker(arm64),喂测试音频确认中文效果与可起服务 ← 风险最高,先证伪
2. 定协议最小事件集(本文 §3 细化成约定)
3. orchestrator 骨架:WebSocket + 调 FunASR + 调 vLLM + 回事件
4. 桌面客户端:摘掉本地识别,接协议,保留 UI/剪贴板
5. 端到端联调 → 对齐 §8 验收
6. 收尾:入口统一、基本健壮性

> 第 1 步是闸门:FunASR 在这台 arm64/Blackwell 上 Docker 化若不顺,要么换 ASR 候选(faster-whisper),要么调整方案——**所以先做它,别先写客户端**。
